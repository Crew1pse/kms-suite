# workload-identity

Короткоживущие X.509-SVID в стиле SPIFFE/SPIRE вместо долгих сертификатов, выпущенных `setup_mtls.sh` на годы.

- **Идентичность** = единственный URI SAN `spiffe://<домен>/<путь>`; CA игнорирует ID из CSR и выдаёт аттестованный.
- **Аттестация**: одноразовый join-токен (хранится хэш, сжигается до выдачи, TTL). Ключ генерирует сам агент.
- **TTL ≤ 1 ч** (по умолчанию 10 мин), **ротация на половине срока с новым ключом**; продление идёт по действующему SVID.
- **Ротация CA**: trust bundle с несколькими CA, период перекрытия, затем `retire_old_cas`.
- **Проверка**: подпись, срок (SVID и CA), не-CA лист, один URI SAN, trust domain, ожидаемый ID.
- **Реальные TLS 1.3-рукопожатия** в тестах: просроченный SVID, чужой CA, нет клиентского сертификата, валидный сертификат чужого сервиса.

## Аттестация узла по TPM (`softtpm.py`, `node_attest.py`)
Вместо одноразового токена узел доказывает, **что он за машина и в каком состоянии загружен**:
1. EK-сертификат подписан доверенным производителем TPM и не отозван;
2. credential activation: секрет зашифрован на EK и привязан к имени AK - расшифровать может только TPM, где живут и EK, и этот AK;
3. свежий quote, подписанный AK, над `nonce + хэш CSR` (ключ SVID привязан к аттестации) с жёстким набором PCR;
4. event log при проигрывании даёт те же PCR, и все измерения разрешены политикой (опционально ещё эталонные digest).
SPIFFE ID узла выводится из EK: `spiffe://<домен>/node/<хэш EK>`. Демо: `python demo_attestation.py`.
Тесты (26) - атаки: программный «TPM» без сертификата производителя, украденный EK-сертификат, AK вне TPM, повтор quote,
подмена CSR после quote, quote по меньшему набору PCR, руткит в ядре, поддельный event log, отозванный EK; 16 мутаций, пойманы все, кроме эквивалентной.
**Это модель протокола, а не TPM**: нет аппаратной защиты ключей, нет реального TPM2 (tpm2-pytss, TCG-форматы quote и EK-сертификатов
не соблюдены), нет измеренной загрузки реального ядра. Реальная прослойка - `tpm2-tools`/go-tpm и vendor-цепочки EK.

## Интеграция с KMS
`COORDINATOR_SPIFFE_ID=spiffe://kms.local/coordinator` в `threshold-kms` включает авторизацию по URI SAN (CN при этом
не даёт доступа). `python issue_kms_certs.py certs/ 5` выпускает набор. Запуск: `pytest && python demo.py`.

## Честные ограничения
- Это модель SPIRE, а не он сам: нет workload API по сокету, нет node-аттестации (AWS/K8s/TPM), нет федерации доменов.
- Join-токен - слабая аттестация (кто украл до использования, тот получил идентичность); для узлов есть TPM-аттестация (ниже).
- Нет отзыва: защита только короткий TTL. Окно компрометации = остаток TTL.
- CA-ключ в памяти процесса; в проде - HSM/Vault (см. `vault-poc`).
- Не аудировано. Рабочая интеграция с запущенным `node.py` проверена на уровне `getpeercert()` и юнит-тестов; полный
  стенд KMS на SVID не гонялся.
