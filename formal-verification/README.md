# formal-verification

Символьный анализ протоколов из `../e2ee-messenger`: вместо «тесты проходят» - **полный перебор всех сочетаний утечек
ключей** и ответ, при каких из них ключ сессии раскрывается.

## Что внутри
- `src/symbolic.py` - движок Дулева-Яо с теорией Диффи-Хеллмана (g^(xy)=g^(yx)), пассивный атакующий, поиск минимальных наборов утечек.
- `src/models.py` - X3DH (с одноразовым prekey и без, мутанты без любого DH, гибрид с ML-KEM) и корневая цепочка Double Ratchet.
- `x3dh.pv` - та же модель X3DH на языке ProVerif (**не запускалась здесь**, см. ниже).
- `tests/test_model_vs_implementation.py` - **мост к коду**: для всех 32 наборов утечек (16 без prekey) настоящий код
  `e2ee.py` раскрывается ровно там, где предсказывает модель; «излечение» Double Ratchet по модели совпадает с измеренным на реальном коде для 12 случаев.
- Активные атаки на реальном коде: подмена личности при утечке SPK, KCI, отражение, склейка сессий, misbinding.

Запуск: `pip install -r requirements.txt pytest && pytest && python demo.py`

## Что показал анализ (все пункты подтверждены на коде)
1. Ключ X3DH раскрывается ровно тремя минимальными наборами: `ek_a+ik_a`, `ek_a+spk_b`, `ik_b+spk_b+opk_b`. Никакая одиночная утечка не опасна.
2. **Forward secrecy держится только с одноразовым prekey.** Без него утечка долгоживущих `ik_b+spk_b` раскрывает все прошлые сессии. Это известный компромисс Signal; теперь он посчитан, а не заявлен.
3. Каждый из DH в KDF нужен: убрать DH1 - и достаточно утечки одного эфемерного ключа (тест-мутант).
4. **Утечка SPK = подделка чужой личности перед владельцем** (подтверждено атакой на реальном коде). Утечка одного `ik_b` - нет (KCI-устойчивость).
   Вывод для кода: в `PrekeyStore` добавлена **ротация SPK** с хранением одного предыдущего поколения; после двух ротаций украденный SPK бесполезен.
5. Гибрид PQXDH: каждый минимальный набор содержит `ss_kem`. Квантовый атакующий, знающий ВСЕ DH-секреты, ключ не получает.
6. Double Ratchet лечится за 2-3 ратчет-шага после кражи состояния; число зависит от того, чьё состояние и в какой момент украдено.
7. **Реальный баг, найденный попутно:** поле `from` конверта вне криптографии - relay мог выдать сообщение Алисы за сообщение Кэрол.
   Исправлено в `Client` (один ключ идентичности - одно имя). На первом контакте остаётся неустранимая граница TOFU.

Проверено 39 тестами и мутациями движка/модели/кода (11 поломок, все убиты; один выживший мутант привёл к новому тесту).

## Честные ограничения
- **Это не Tamarin и не ProVerif.** Они недоступны в песочнице (apt и GitHub закрыты). Мой движок - пассивный атакующий и
  статическая выводимость ключа. Он **не доказывает** аутентификацию и устойчивость к активным атакам: эти свойства проверены только
  конкретными атаками на код (это тесты, а не доказательство отсутствия других атак).
- `x3dh.pv` написан по памяти и никогда не запускался; возможны синтаксические ошибки. Запустите `proverif x3dh.pv`:
  ожидаем, что секретность `secret_msg` и аутентификация (для честной Алисы) держатся. Если нет - пришлите вывод.
- Double Ratchet смоделирован на уровне корневой цепочки (без цепочек сообщений и пропусков).
- Нет модели FROST/DKG: она требует модели Шнорр-подписи и раундов с активным атакующим, то есть настоящего инструмента.
- Модель считает примитивы идеальными (KDF - случайный оракул, DH без атак на малые подгруппы).
