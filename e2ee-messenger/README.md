# e2ee-messenger

Сквозное шифрование по схеме Signal: **X3DH** (асинхронный обмен ключами по prekey-bundle) + **Double Ratchet**.
X25519, Ed25519 (подпись signed prekey), HKDF-SHA256, HMAC-SHA256, AES-256-GCM. Relay недоверенный.

Запуск: `pip install -r requirements.txt pytest hypothesis && pytest && python demo.py`

## Что гарантируется и проверено тестами (60)
- Forward secrecy: украденное состояние не читает прошлые сообщения.
- Post-compromise security: после нескольких DH-шагов украденное состояние слепнет.
- Out-of-order, потеря сообщений, лимит пропусков (`MAX_SKIP`), отказ от повторов.
- Подмена заголовка/шифртекста/AD отвергается, **состояние при этом не меняется** (коммит после аутентификации).
- Подпись SPK привязана к ключу идентичности; одноразовые prekey реально одноразовые.
- Ротация signed prekey (`PrekeyStore.rotate_spk`): одно предыдущее поколение для сообщений «в полёте», старше стирается.
  Нужна потому, что утечка SPK позволяет выдавать себя за кого угодно перед владельцем (подтверждено в `../formal-verification`).
- Один ключ идентичности - одно имя: поле `from` вне криптографии, relay мог переподписать чужое сообщение; найдено формальным анализом, исправлено.
  На первом контакте имя назначает relay - это граница TOFU, закрывается только сверкой safety number.
- TOFU: смена ключей собеседника -> `IdentityChanged`; safety number для сверки по другому каналу.
- Мутационная проверка: 15 намеренных поломок кода, 14 убиты тестами, 1 эквивалентный (повтор всё равно
  ловится аутентификацией AES-GCM, явная проверка - вторая линия защиты).

## Честные ограничения
- Это учебная реализация, **не аудирована**, не совместима с libsignal по формату (свои info-строки и сериализация).
- Нет дедупликации/упорядочивания на уровне транспорта, нет групповых чатов, нет sealed sender, нет скрытия метаданных
  (relay видит, кто кому и когда пишет).
- Python не стирает ключи из памяти; приватные ключи в `bytes`.
- Ключ идентичности не меняется и не хранится на диске; сессии живут только в памяти.
- Подмена bundle самим relay на первом контакте ловится только ручной сверкой safety number (как в Signal).
- Базовый X3DH не защищён от «записать сейчас, взломать потом»: для этого есть PQXDH (раздел ниже), но в `Client` он не подключён.

## PQXDH (постквантовый вариант)
`src/pqxdh.py`: X3DH + ML-KEM-768 (FIPS 203, библиотека `kyber-py`). Ключ сессии секретен, пока устойчива хотя бы одна из частей.
Тесты (14, 12 мутаций убиты) показывают обе стороны гибрида: атакующий со всеми DH-секретами не получает ключ без секрета KEM, и наоборот.
Цена (`python bench_pq.py`): bundle 192 -> 1440 байт, init-заголовок 104 -> 1192 байт, инициация ~0.4 -> ~3.3 мс.
Ограничения: `kyber-py` - чистый Python, не constant-time, для исследования, не для продакшена; в `Client`/`Relay` PQXDH не подключён
(работает на уровне протокола + Double Ratchet); подпись идентичности остаётся Ed25519 (классическая), то есть защита от
квантовой *подделки* личности (активный MITM) не обеспечена - только от пассивной записи трафика.
